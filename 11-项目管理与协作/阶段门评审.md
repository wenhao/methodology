# 阶段门评审（Stage-Gate Process）

> **一句话定义**：把大项目切成若干阶段，阶段之间设"门"——过门必须带着事先约定的交付证据，由授权人按明确标准裁决"过、返工、还是杀"，防止沉没成本绑架后续投入。

## 是什么

Robert Cooper 为新产品开发提出的治理框架（Stage-Gate®），现已成为大型项目管理通用范式。**Stage（阶段）**：资源投入段，每阶段末产出定义明确的交付包；**Gate（门）**：决策检查点，独立于执行——门上不干活，只裁决。

三个关键设计：
- **门有独立的裁决人（Gatekeeper）**：不是执行团队自评，是有授权的决策者（通常跨职能）
- **门有事先写明的通过标准**：数据指标在前，判断在后，防止"气氛到了就放行"
- **门的输出不只"过"**：通过 / 有条件通过（带整改项）/ 返工 / 回收资源（杀）——**"杀"是一等选项**，这是与普通进度评审的本质区别

## 核心操作

1. **设计阶段与门**：典型如 阶段0 机会确认 → 门1 立项 → 阶段1 可行性 → 门2 方案选定 → 阶段2 执行 → 门3 交付验收 → 阶段3 上市/运维 → 门4 复盘关闭
2. **每扇门预先定义三件套**：交付物清单（什么证据）、通过标准（什么算合格）、裁决人（谁拍板）
3. **阶段内自主、门口严检**：阶段内给执行团队最大自由（敏捷），门口用外部视角严格验收（与红队检验联动）
4. **裁决记录留档**：每个门的结论、依据、附带条件写入项目档案——后续复盘与审计的锚点
5. **允许跳门与快速通道**：低风险小项目允许并行阶段/合并门，避免流程一刀切拖死小项目

## 工作应用

- **大型研究项目立项**：门1 立项必须交"信息价值论证"（这项研究能改变什么决策？值多少钱？）——大量"看起来有意思"的选题死在门1，资源省下给真问题
- **建模与交付验收**：门3 交付验收的通过标准事先写明（样本外误差阈值、文档完整性清单）——防止"模型能跑了"就算交付
- **供应商项目管控**：外包数据/系统开发按阶段付款（门通过=付款节点），比一口价尾款制主动权大得多
- **个人项目的防自欺**：自学计划、副业项目设自检门——"三个月后若达不到 X 就停"，事先写下杀掉标准，对抗沉没成本

## 局限与陷阱

- 门变橡皮图章：裁决人事先知道了结论、或标准模糊依赖现场判断——门就退化为进度汇报会
- 流程税：门太多太重，小项目被治理成本拖死——按项目规模分级配置门的数量与严格度
- 阶段划分僵化：创新性高的工作阶段产出形态会变，门标准要随学习到的信息修订（但不许事后偷偷改）
- 裁决人失能：Gatekeeper 缺专业知识时被执行团队的叙事绑架——配齐跨职能裁决人或引入外部评审
